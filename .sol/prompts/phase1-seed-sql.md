## Deliverable 1 — `seed/`

A deterministic generator (fixed RNG seed, so re-running produces byte-identical output) that
writes JSON into `data/seed/`.

### `seed/generate.py`

Runnable as `.venv/bin/python -m seed.generate` (add `seed/__init__.py`). Writes:

#### A. `data/seed/students.json` — the demo students

Shape:

```json
{
  "generated_at": "2026-08-06T00:00:00Z",
  "note": "SYNTHETIC SEED DATA — generated by seed/generate.py, not real users",
  "students": [
    {
      "user_id": "stu_maya_chen",
      "display_name": "Maya Chen",
      "grade_level": "11th grade",
      "subjects": ["AP Chemistry", "Algebra II"],
      "memories": [ <Memory>, ... ]
    }
  ]
}
```

Where `<Memory>` is exactly the field set of `app.contracts.Memory`:

```json
{
  "memory_id": "mem_0a1b2c3d",
  "memory_type": "profile",             // profile | semantic | procedural | episodic
  "content": "Maya is an 11th grader taking AP Chemistry and Algebra II.",
  "user_id": "stu_maya_chen",
  "agent_id": "memoryledger-tutor",
  "app_id": "memoryledger",
  "project_id": "hackathon",
  "session_id": null,                    // set only for episodic memories
  "score": 0.87,                         // retrieval relevance 0..1
  "created_at": "2026-06-14T18:22:00Z",
  "updated_at": "2026-06-14T18:22:00Z",
  "metadata": {"week": 1, "topic": "stoichiometry"}
}
```

Generate **3 students**. The first, `stu_maya_chen`, is the demo student and needs the richest
history. Requirements per student:

- **~8 weeks of tutoring history**, timestamps spread realistically across those weeks
  (weekday evenings, 2–4 sessions a week). Latest activity should be within the last few days
  relative to `2026-08-06`.
- **All four memory types present**, in roughly these proportions:
  - `procedural` (Skills / tier 0): 6–10. How the tutor should behave. e.g. *"When Maya asks for
    an answer directly, give a hint first and ask her to attempt a step."* These are the tutor's
    operating rules learned over time. They must read like operating instructions, not facts.
  - `profile` (tier 1): 10–16. Durable facts about the learner: grade, courses, exam dates,
    learning style, accommodations, goals, time zone, name of their teacher, motivation.
  - `semantic` (tier 2): 25–40. What the learner knows and does not know. e.g. *"Maya can balance
    redox half-reactions in acidic solution but not basic."* Include misconceptions, mastered
    concepts, and shaky concepts. These are the ones that change on a scale of days.
  - `episodic` (tier 3): 40–70. Session events. e.g. *"On 2026-07-22 Maya spent 25 minutes on
    limiting-reagent problems and got 4/6 correct."* Each carries a `session_id`.
- **Total memory content for the demo student should be substantial** — aim for the full set to be
  roughly 3,000–6,000 tokens of text, because the cache-minimum is 1,024 tokens and the demo needs
  tiers 0+1+2 to comfortably clear it. Individual memories are 1–3 sentences; volume comes from
  count, not from padding any one memory. Verify the total with `tiktoken` (`cl100k_base`) and
  print the per-tier token counts when the generator runs — Fable needs those numbers.
- **Content must be plausible, specific, and non-repetitive.** Real chemistry and algebra concepts,
  real misconceptions students actually have. No lorem ipsum, no "Memory number 47". Vary sentence
  structure. If two memories say nearly the same thing, that is a bug.

**Planted ablation memories** — the ablation harness in Phase 3 must be able to prove it works in
both directions. Add exactly two extra memories to `stu_maya_chen`:

1. A **junk** memory that cannot possibly affect any tutoring answer, but is long enough to cost
   real tokens (~120–200 tokens). It must look like something a naive memory system would actually
   store — e.g. a verbose restatement of a UI interaction, or a logged preference about something
   the tutor never uses. Mark it `"metadata": {"planted": "junk", ...}`.
   Do NOT make it obviously labelled inside the `content` string — the harness must discover it
   empirically, not read the label.
2. A **critical** memory whose removal would clearly change an answer — e.g. *"Maya's AP Chemistry
   exam is on 2026-09-12 and she has requested all study plans be scheduled backward from that
   date."* or a stated accommodation the tutor must honour. Mark it
   `"metadata": {"planted": "critical", ...}`.

Also emit `data/seed/planted.json` listing the two `memory_id`s and which is which, so the harness
and Fable's tests can assert against it without string-matching content:

```json
{"junk": ["mem_xxxx"], "critical": ["mem_yyyy"]}
```

#### B. `data/seed/conversations.json` — scripted demo conversations

The experiment runner (Fable's `scripts/experiment.py`) replays a fixed conversation N times in
each mode. Provide it:

```json
{
  "note": "SYNTHETIC SEED DATA",
  "conversations": [
    {
      "conversation_id": "conv_stoich_review",
      "user_id": "stu_maya_chen",
      "title": "Stoichiometry review before the unit test",
      "turns": ["Can you help me with limiting reagents?", "...", "..."]
    }
  ]
}
```

Provide **3 conversations** of **6–8 turns each** for `stu_maya_chen`. Turns are the student's
messages only (the tutor's replies come from the model). They must be realistic student messages
with typos and shorthand, escalating in difficulty, and they must plausibly trigger retrieval of
different memory subsets across turns — that is what makes tier 3 churn while tiers 0–2 hold still.

#### C. `data/seed/fleet.json` — multi-tenant fleet

~5,000 synthetic tenants for the dashboard's fleet view. Keep it to summary rows, not full memory
sets, so the file stays a few MB:

```json
{
  "note": "SYNTHETIC SEED DATA — labelled as such in the UI",
  "generated_at": "...",
  "tenants": [
    {
      "tenant_id": "tnt_000001",
      "name": "Northgate Tutoring",
      "plan": "growth",                       // starter | growth | scale
      "students": 412,
      "memories_total": 38104,
      "calls_30d": 91240,
      "avg_memories_per_call": 22.4,
      "naive_cost_30d_usd": 1840.22,
      "tiered_cost_30d_usd": 690.11,
      "cache_hit_rate": 0.63,
      "eviction_candidates": 1204,
      "wasted_spend_30d_usd": 143.90
    }
  ]
}
```

Distributions must be plausible and heavy-tailed, not uniform: most tenants small, a handful very
large. Derive `tiered_cost_30d_usd` from `naive_cost_30d_usd` and `cache_hit_rate` with a stated
formula in a comment rather than drawing both independently — the numbers must be internally
consistent, because a judge may check that the ratio matches the hit rate. Organisation names
should be plausible tutoring/edtech company names, generated by combining word lists, all clearly
fictional.

## Deliverable 2 — `sql/`

Snowflake DDL and analytics. These will not run tonight (no credentials), so they must be
syntactically careful and reviewable. Mark any line you are not certain about with a
`-- VERIFY-AT-EVENT:` comment.

### `sql/01_ddl.sql`

`CREATE DATABASE IF NOT EXISTS MEMORYLEDGER;` + schema + four tables. Columns must match Fable's
dataclasses in `app/contracts.py` exactly — same names, snake_case → SNOWFLAKE UPPER_CASE:

**`CALL_LOG`** — one row per inference call
`CALL_ID STRING PK, SESSION_ID STRING, USER_ID STRING, TS TIMESTAMP_NTZ, MODE STRING,
MODEL STRING, INPUT_TOKENS NUMBER, OUTPUT_TOKENS NUMBER, CACHED_TOKENS NUMBER,
CACHE_WRITE_TOKENS NUMBER, COST_USD FLOAT, COST_UNCACHED_USD FLOAT, COST_CACHED_USD FLOAT,
COST_WRITE_USD FLOAT, COST_OUTPUT_USD FLOAT, LATENCY_MS FLOAT, BREAKPOINT_COUNT NUMBER,
TIER_TOKENS VARIANT, BASELINE_COST_USD FLOAT`

**`MEMORY_INJECTIONS`** — one row per (call, memory)
`CALL_ID STRING, MEMORY_ID STRING, USER_ID STRING, TS TIMESTAMP_NTZ, TIER NUMBER,
MEMORY_TYPE STRING, TOKENS NUMBER, WAS_CACHED BOOLEAN, ATTRIBUTED_COST_USD FLOAT`

**`MEMORY_REGISTRY`** — current state of each memory
`MEMORY_ID STRING PK, USER_ID STRING, MEMORY_TYPE STRING, CONTENT_HASH STRING, TIER NUMBER,
STABLE_CALLS NUMBER, TOKENS NUMBER, FIRST_SEEN TIMESTAMP_NTZ, LAST_SEEN TIMESTAMP_NTZ`

**`ABLATION_RESULTS`**
`ABLATION_ID STRING PK, MEMORY_ID STRING, USER_ID STRING, TS TIMESTAMP_NTZ, PROMPT STRING,
BASELINE_ANSWER STRING, ABLATED_ANSWER STRING, SIMILARITY FLOAT, VERDICT STRING,
TOKENS_SAVED NUMBER, MONTHLY_COST_USD FLOAT`
(`VERDICT` ∈ `'evict'`, `'keep'`, `'inconclusive'`.)

Add clustering keys only where they obviously help; do not over-engineer.

### `sql/02_rollups.sql`

Views/queries the dashboard needs. At minimum:
- `V_MEMORY_MONTHLY_COST` — per memory: injections, total tokens, cache hit rate,
  30-day cost, projected monthly cost.
- `V_CACHE_HIT_BY_TIER` — cache hit rate and token volume by tier and mode.
- `V_MODE_COMPARISON` — mean cost per call and per conversation, naive vs tiered, with stddev.
- `V_EVICTION_CANDIDATES` — join `V_MEMORY_MONTHLY_COST` to `ABLATION_RESULTS`, ranked by
  monthly cost among memories whose verdict is `'evict'`.

### `sql/03_reconcile.sql`

A query comparing our `CALL_LOG` against Snowflake's
`SNOWFLAKE.ACCOUNT_USAGE.CORTEX_REST_API_USAGE_HISTORY` (or the correct view name — mark it
`-- VERIFY-AT-EVENT:` since you cannot check it tonight), bucketed by hour, showing our token
counts vs theirs and the delta. Include a header comment stating that this view lags up to
45 minutes and is therefore a post-hoc credibility check, never the live meter.

What to run, in what order, and what each file is for. Five to fifteen lines.
