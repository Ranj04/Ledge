# Ledger SQL

Two files, one schema, two warehouse dialects — and as of T4 one of them runs. `01_ddl.sql`
is generated from `migrations/`; `02_rollups.sql` is the four dashboard views. Run them in
numeric order, in one session, with a role allowed to create the database and schema.
Do not use account-usage reconciliation for the live meter because it can lag 45 minutes.

| File | What it is | Edit? |
|---|---|---|
| `01_ddl.sql` | The Snowflake rendering of `migrations/`, generated by `python scripts/migrate.py --dialect snowflake --dry-run > sql/01_ddl.sql`. Creates `MEMORYLEDGER.LEDGER`, `SCHEMA_MIGRATIONS` and the ledger tables. | **No — regenerate.** |
| `02_rollups.sql` | The four dashboard views, hand-written in the intersection of DuckDB and Snowflake SQL: `CASE` not `IFF`, `CURRENT_TIMESTAMP - INTERVAL '30 days'` not `DATEADD`, `::DOUBLE` not `::FLOAT`. `QUALIFY`, `COUNT_IF` and the window functions are native to both. | Yes — views are dashboard code, not schema. |

The schema is declared once, in `migrations/`, and rendered by `app/telemetry/migrate.py`
to SQLite, DuckDB and Snowflake through five logical types. Every store creates its tables
from that declaration, reads them back and compares before recording a version (D38);
`tests/test_migrations.py` asserts the three renderings carry the same columns in the same
order.

## DuckDB — runs, no account

`LEDGER_PROVIDER=duckdb` (file at `DUCKDB_PATH`, default `data/ledger.duckdb`).
`DuckDBLedgerStore.init_schema` applies `migrations/` and then loads `02_rollups.sql` as-is,
so every view exists in every DuckDB ledger. From the shell:

```
python scripts/migrate.py --dialect duckdb            # apply; prints the version reached
python scripts/migrate.py --dialect duckdb --dry-run  # the DDL, never connects
```

`tests/test_duckdb_store.py` is the point of the backend: it writes one set of records — a
real conversation in both modes through the simulator and `build_records` — to SQLite and to
DuckDB, asserts every dashboard query returns the same numbers, and reads every view back
against the store's own query for the same figure. That test found the views projecting a
different monthly cost from the dashboard (D44); the definition is now shared.

## Snowflake — written, unexercised

Run `01_ddl.sql` then `02_rollups.sql` in one Snowsight session (the first selects
`MEMORYLEDGER.LEDGER`; the second deliberately carries no `USE SCHEMA`, which DuckDB would not
parse). Or start the service with `LEDGER_PROVIDER=snowflake`; `init_schema` applies the same
migrations. The event has passed with no Cortex entitlement on the trial account (D28), so the
migrator, the D38 verification, the lifecycle `MERGE`s and the views as now written have never
run against a real account; the 2026-08-07 session exercised the earlier hand-written DDL and
inserts only. Each unverified line carries `VERIFY-WITH-CREDENTIALS`.
